# rhwp-behavior.md — `hwp` 스킬 동작 명세 (Behavioral Spec)

> **KEYSTONE 문서.** 이 파일은 `hwp` Claude 스킬이 감싸는 rhwp 엔진(`@rhwp/core`)의 **실제 동작**에 대한 단일 진실 공급원(single source of truth)입니다. 각 규칙은 `test/spec/` 아래 테스트 하나로 매핑됩니다(끝의 Catalog→Rule 추적표 참조). 스킬은 어떤 경우에도 사용자 문서를 **조용히 손상시켜서는 안 됩니다(MUST NOT silently corrupt)** — 그래서 "조용한 실패(silently dropped)" 케이스는 전부 여기에 명시되고 테스트로 고정됩니다.

- **UNVERIFIED** — 등급이 아니라 **한정어**. 스킬 쪽 동작은 테스트되지만 기저 엔진/포맷 동작을 확인할 입력이 없을 때 등급 뒤에 붙이며, **무엇이 비어 있는지**를 반드시 함께 적는다(현재: 규칙 47 — 진짜 변경추적 `.hwpx`가 없다).
- **SPEC-FIRST** — 아직 스킬에 구현되지 않은 동작을 규정(테스트가 요구 사양을 정의). *현재 이 등급인 규칙은 없다* — 규칙 4·5·6이 마지막이었고 `extract_tables.mjs`에 구현되면서 AGENT-SIDE로 승격되었다.

## 1. Tables (표 읽기/구조)

1. **머지 원점 저장(merge-origin storage).** 병합된 셀의 텍스트는 병합 범위의 **원점(top-left) 셀에만 한 번** 저장되며, 덮인(covered) 위치에는 셀이 존재하지 않는다. 스킬은 **반드시 `getCellInfo`가 반환하는 `{row, col, rowSpan, colSpan}`로 주소 기반 그리드를 재구성**해야 하며(주의: `cellAddr`라는 필드는 **없다**), 문서(컨트롤) 순서로 셀을 읽으면 병합 데이터가 조용히 어긋난다. — **CONFIRMED.** `test:` `fixture-table.hwpx`의 `getCellInfo(0,0,2,0)`가 `{"row":0,"col":0,"rowSpan":1,"colSpan":4}`를 반환하고, 그리드 재구성 시 덮인 위치가 원점 셀에서 채워지는지 단정.
2. **`cellCount`는 원점 셀만 센다.** `getTableDimensions.cellCount`는 **원점 셀 수**이며 `rowCount*colCount`가 아니다. 병합이 있으면 `cellCount < rowCount*colCount`. 셀 반복 루프 상한으로 `cellCount`를 쓰고, 전체 그리드는 span으로 복원한다. — **CONFIRMED.** `test:` `fixture-table.hwpx`에서 `getTableDimensions(0,0,2)` = `{rowCount:3,colCount:8,cellCount:18}` → `18 < 24` 단정.
3. **중첩 표(nested tables)는 셀 문단 내부에 존재.** 평탄(flat) 문단 레벨이 아니라 **각 원점 셀의 문단**을 순회하며 `*ByPath` API로 컨트롤을 프로브해야 발견된다(`getCellParagraphCount` + `getTableDimensionsByPath(cellPath)`). 부모→자식 깊이 우선. **셀 문단당 컨트롤 인덱스 7을 넘는 표는 누락**된다(`NESTED_PROBE_MAX=8` 하드코딩). — **CONFIRMED (source+probe).** `test:` 중첩 표가 부모 셀 메타로 발견되고, 8번째 이후 컨트롤은 미탐지임을 단정(중첩 샘플 부재 시 probe-limit 단위 테스트로 대체).
4. **범례/작성요령 표 필터링은 에이전트측.** 데이터 표 뒤에 구분자 없이 범례/작성요령 표가 붙는다. 엔진은 구분하지 않으므로 **헤더 행 키워드**로 분류한다: 첫 행에 `연번`/`학위과정`/`성명`/`발표형식` → 데이터; `구분`/`교육연구단 학문분야`이고 `연번` 없음 → 범례(데이터 추출 시 드롭 권장). — **AGENT-SIDE (구현됨: `extract_tables.mjs --data-tables-only`).** 판정은 **보수적**이다: 확신이 없으면 KEEP하고, 첫 행이 `구분`/`작성요령`으로 시작하면서 `연번`이 없을 때만 DROP하며 드롭 사실을 stderr로 알린다. `test:` `test/spec/tables.test.mjs` — 플래그가 정상 동작하고, `fixture-table.hwp`의 숫자 데이터 표를 드롭하지 **않음**을 단정.
5. **마커형 vs 라벨형 폼.** 폼 상세 컬럼은 두 패턴 중 하나: **(a) 마커형** — 각 줄이 원문자 `①~⑩`로 시작(마커로 split, 나머지가 값, 마커 없는 줄은 직전 키에 누적); **(b) 라벨형** — `라벨: 값`/`라벨：값`(한/전각 콜론). 각 필드는 **표의 별도 ROW(rowSpan)**에 있으며 멀티라인 셀이 아니다. 엔진은 구분하지 않는다. — **AGENT-SIDE (구현됨: `extract_tables.mjs --detect-form-type`).** 그리드를 재구성하지 않고 표마다 `formType: 'marker' | 'label' | 'plain'`을 **주석으로만** 붙인다. `test:` `test/spec/tables.test.mjs` — 플래그 동작 및 출력 형태 단정.
6. **플레이스홀더 정규화는 에이전트측.** `'-'`, `'X'`, `';N'`, `'N'`, `'번호'`, `'해당없음'`, `'N/A'`, `'DOI 번호'`, 괄호 변형 등은 빈 문자열로 정규화한다. rhwp는 플레이스홀더와 데이터를 구분하지 않는다. — **AGENT-SIDE (구현됨: `extract_tables.mjs --drop-empty`).** 방출되는 그리드 텍스트에만 적용된다. `test:` `test/spec/tables.test.mjs` — 플래그 동작 및 출력 형태 단정.
7. **풀-와이드 공백은 U+2007(figure-space).** 표/수치 텍스트의 전각 공백은 **U+2007**(figure-space)로 추출되며 U+3000(ideographic-space)이 아니다. 필드 공백 검색/매칭은 **U+2007 기준**(또는 `\s`)으로 해야 한다. — **CONFIRMED.** `test:` HWPX 샘플 추출 텍스트에 U+2007 존재, U+3000 부재 단정.
8. **`getPageTextLayout`은 근사 레이아웃.** `{text,x,y,w,h,charX[],fontFamily,fontSize,...}` 런 배열을 y 기준 정렬로 반환하며, 같은 줄의 런은 **y±(런 높이/2)** 오차로 묶인다. 컬럼/행 구조 추론용이며 **픽셀 정확 위치가 아니다**(정밀 렌더는 `enhanced/` CLI render/export-png). — **CONFIRMED.** `test:` `fixture-table.hwp` page 0에서 런을 `floor(y)`로 그룹화해 줄 묶음이 안정적인지 단정.

## 2. Editing / Round-trip (편집 및 저장 왕복)

> **핵심 원리(raw_stream 캐시).** 진짜 .hwp는 원본 `section.raw_stream` 바이트를 캐시한다. 직렬화기는 캐시된 raw_stream이 있으면 **IR 변경을 무시하고 캐시 바이트를 그대로 방출**한다. 따라서 **`raw_stream`을 null로 비우는 API만** .hwp 왕복에서 안전하다. HWPX 입력은 raw_stream이 없어 모든 편집이 IR에서 재구성된다.
>
> 이 캐시 자체는 (성능을 위한) 정상 설계이며, 0.7.16부터는 `replaceAll`을 포함한 **모든 변형 API가 캐시를 무효화**한다(규칙 9). 문제가 되는 것은 캐시를 비우지 않고 IR만 고치는 경로이며, 엔진이 모델링하지 않는 **메모는 여전히 이 캐시로만 살아남는다**(§2a) — 그래서 메모 있는 섹션을 편집하면 메모가 사라진다.
>
> **검증 메커니즘 주의:** `verify.mjs`의 `probeTextCount`는 `replaceAll(q, q)`(자기 자신으로 치환하는 no-op)의 **match COUNT만** 사용한다 — 본문+셀+텍스트박스 **전체 문서**를 커버한다(`searchText`는 본문만). 모든 왕복 단정은 이 카운트에 의존한다.

9. **`replaceAll()`은 진짜 .hwp에서도 안전하다 (0.7.16+).** `replaceAll(query, replacement, caseSensitive)`는 이제 `section.raw_stream` 캐시를 null로 비우므로 저장 시 편집이 **생존한다**. 본문·셀·글상자를 한 번의 호출로 커버한다. — **CONFIRMED (0.7.19 프로브).**
   > **0.7.15까지는 정반대였다.** raw_stream이 무효화되지 않아 `replaceAll` 편집이 **에러 없이 사라졌고**(FAILS-SILENTLY, 본문·셀 동일), 스킬은 규칙 11의 `searchAllText` + delete/insert 경로로 우회했다. 업스트림 수정: `d0e866da` (PR #1398, issue #1385), 0.7.16 릴리스 포함.
   > **재검증 근거:** 실문서(2섹션, 매치 182건 중 99건이 셀 내부)에서 0.7.15는 182건 **전량 유실**, 0.7.19는 182건 **전량 생존**. 합성 픽스처(`fixture-table.hwp`) 본문·셀 각각 6/6 생존.
   > `test:` `fixture-table.hwp`에 `replaceAll` 후 export→reload에서 치환 문자열이 존재하고 원본이 사라졌음을 단정(`test/smoke.test.mjs`, `test/spec/edit-matrix.test.mjs`). **이 테스트가 빨개지면 엔진이 회귀한 것** — 규칙 11의 우회 경로를 복원할 것.
10. **`replaceText()`(위치 기반)는 안전하다.** `replaceText(section, para, char_offset, length, new_text)`는 검색이 아닌 **위치 기반 치환**이며 raw_stream을 null로 비워 **.hwp 왕복 생존**. `replaceAll`과 다르다. — **CONFIRMED.** `test:` `searchText('△')`로 위치 찾고 `replaceText(0,23,3,1,'REPLACED_POS')` → reload 시 치환 텍스트 count=1 단정.
11. **검색 후 insert/delete 경로도 여전히 유효하다 (regression fallback).** **(1) `searchText`/`searchAllText` 순회로 위치 수집(역순) → (2) `deleteText`/`deleteTextInCell`로 제거 → (3) `insertText`/`insertTextInCell`로 삽입.** `insertText`/`deleteText` 계열은 raw_stream을 null로 비워 편집이 생존한다. 0.7.15까지는 이것이 .hwp 찾기/바꾸기의 **유일한** 안전 경로였고 `lib/safe-edit.mjs`가 이 시퀀스를 구현했다. 규칙 9가 수정된 지금은 `replaceAll` 한 줄로 대체되었으나, **엔진이 회귀하면 되돌아올 경로**이므로 명세에 남긴다. — **CONFIRMED.** `test:` 검색→삭제→삽입 시퀀스가 reload에서 일관됨을 단정.

## 2a. Memos (메모/주석 — 조용한 삭제)

> **핵심 원리.** rhwp 엔진의 IR은 **메모(메모/주석, comment annotation)를 모델링하지 않는다.** 메모는 오직 HWP5의 **섹션별 `raw_stream` 패스트패스**로만 살아남는다 — 그 섹션을 건드리는 편집이 일어나는 순간, 섹션은 메모를 한 번도 담은 적 없는 IR로부터 재직렬화되고 그 안의 모든 메모가 **저장 시 에러 없이 삭제**된다(규칙 9의 raw_stream 메커니즘과 동일 뿌리, 단 여기선 드롭되는 게 *편집*이 아니라 *기존 메모*다).

29. **메모-보유 섹션 편집은 메모를 조용히 삭제한다.** 메모가 들어 있는 섹션에 어떤 편집(`insertText`/`replaceText`/셀 편집 등 raw_stream을 null로 비우는 안전 경로 포함)이라도 가하면, 저장 시 그 섹션의 **모든 메모가 사라진다** — in-memory에선 성공으로 보이고 에러도 없다. 스킬은 편집 전 **메모를 탐지**(`src/lib/memo.mjs` — 순수 JS CFB/ZIP 파서, 무의존성: `detectMemos`/`readMemos`)하고, 메모가 있으면 `assertMemoSafe`가 **편집을 차단**한다(exit `UNSAFE(6)`, `--allow-memo-loss`로만 우회). 메모는 `read.mjs --memos`로 읽을 수 있다. — **CONFIRMED (실제 .hwp에서 검증: 메모 13개, 메모 보유 섹션 1회 편집 후 0개).** `test:` `fixture-memo.hwpx`(메모 1개 "테스트 메모입니다")에서 `detectMemos.count===1`·`readMemos`가 본문을 반환하고, 메모 없는 `fixture-table.hwp`/`fixture-form.hwp`는 `count===0`임을 단정; `assertMemoSafe`가 `--allow-memo-loss` 없이 `EXIT.UNSAFE(6)`로 종료함을 단정.

## 6. Controls / inline objects (인라인 컨트롤 — 구조 프리미티브)

> **핵심 원리.** 컨트롤(표·수식·각주·필드·도형)은 문단 텍스트에서 **폭을 차지하지 않으며**, 그 오프셋은 `getTextRange`와 **같은 좌표계**다. 이것이 인라인 스플라이싱(`lib/blocks.mjs`의 `renderSpan`)을 근사가 아니라 **정확한 연산**으로 만든다. 그리고 "이 컨트롤이 무엇인가"를 묻는 API는 **없다** — 종류는 *throw하지 않는 접근자*로 판별하며, 그 에러 메시지를 잘못 읽으면 데이터가 조용히 사라진다(규칙 32).

30. **인라인 컨트롤은 zero-width이며, 오프셋은 `getTextRange` 좌표계를 공유한다.** `getControlTextPositions(s,p)`는 컨트롤당 문자 오프셋 하나를 **컨트롤 인덱스 순서로** 반환한다. 20자 문단에 수식 2개(오프셋 11·18)와 각주 1개(오프셋 20)를 넣어도 문단은 **여전히 20자**이고 위치는 `[0,0,11,18,20]`이다(앞의 `0,0`은 섹션 첫 문단의 보이지 않는 쌍). *주의: `lib/doc_walk.mjs` 헤더 주석은 이 예를 `[0,0,11,20,20]`으로 적고 있으나, 0.7.19 재프로브 결과는 `[0,0,11,18,20]`이다 — 규칙(zero-width·같은 좌표계)은 그대로이고 예시 숫자만 틀렸다.* 따라서 컨트롤의 렌더 결과를 그 오프셋에 그대로 splice하면 모든 문자가 문서가 놓은 자리에 떨어진다. **또한 모든 섹션의 첫 문단은 offset 0에 보이지 않는 `SectionDef`/`ColumnDef` 컨트롤을 갖는다** — 모든 컨트롤을 렌더 대상으로 취급하면 섹션마다 0번 위치에 유령 마커가 찍히므로, 이들은 `kind:"other"`로 분류되어 **아무 것도 방출하지 않는다**. — **CONFIRMED.** `test:` `test/spec/doc-walk.test.mjs` — "rule 30: inline controls take no space in the paragraph's text" / "rule 30: control offsets are inside the paragraph's text range" / "rule 30: a section's first paragraph carries invisible controls at offset 0"; `test/spec/inline.test.mjs` — "splice: equations and the footnote land at their exact offsets"(인덱스 단정, `includes()` 아님) / "invisible controls: a section's first block renders exactly its own text".
31. **`findNearestControlForward`/`Backward`는 열거자가 아니다 — 컨트롤을 건너뛴다.** 타입까지 얹어주는 값싼 typed sweep처럼 보이지만 실제로는 **에디터 커서 내비게이션**이다. 측정: `fixture-form.hwp`는 컨트롤 8개(문단 0에 3개 — `SectionDef`/`ColumnDef` 포함 —, 문단 2/4/6/8/10에 필드 1개씩, 즉 보이지 않는 쌍을 빼면 6개)를 갖는데 `(0,0,0)`에서 시작한 forward 체인은 **`0/10/0`(type `field`) 단 하나**만 보고하고 `{"type":"none"}`으로 끝난다. `fixture-table.hwpx`는 유일한 표가 문단 0의 컨트롤 2인데 `(0,0,0)` forward 스윕은 **`{"type":"none"}`**, 끝에서의 backward 스윕은 **`{"type":"table",…,"ci":2}`**를 반환한다. 열거는 **반드시 `getControlTextPositions` + probe**로 한다 — 이 API로 열거하면 표가 조용히 누락된다. — **CONFIRMED.** `test:` `test/spec/doc-walk.test.mjs` — "rule 31: findNearestControlForward SKIPS controls (never enumerate with it)" / "rule 31: a forward sweep can miss a table that getControlTextPositions finds". *엔진이 이걸 완전하게 고치면 이 테스트가 빨개진다 — 그때 재고할 신호이지, 조용히 신뢰할 근거가 아니다.*
32. **⚠ THE EQUATION TRAP: 본문 수식을 셀 인덱스 `(0,0)`으로 프로브하면 "표가 아닙니다"가 온다.** `getEquationProperties(s,p,c,0,0)`은 엔진의 셀/표 조회 경로로 라우팅되어 **`지정된 컨트롤이 표가 아닙니다`**를 던진다 — 표 probe가 "이 컨트롤은 건너뛰라"는 뜻으로 쓰는 **바로 그 메시지**다. 표 probe의 에러 처리를 그대로 이식하면 **모든 문서의 모든 수식이 에러 한 줄 없이 사라진다.** 이 규칙은 이 문서에서 가장 손해가 큰 발견이며, `lib/doc_walk.mjs`가 `BODY_EQUATION_CELL` 상수를 두고 호출부에 맨 `-1`을 쓰지 못하게 한 이유다(0이 하나 섞이면 그대로 조용한 데이터 손실). — **CONFIRMED.** `test:` `test/spec/doc-walk.test.mjs` — "rule 32: getEquationProperties with cell (0,0) reports 'not a table' — the trap"(`isNotTableError`는 true, `isNotEquationError`는 **false**임을 단정); `test/spec/inline.test.mjs` — "trap: the renderer FINDS the body equations (a (0,0) probe would lose them)" / "trap: getEquationProperties with cell (0,0) still reports 'not a table'".
33. **본문 수식은 `(-1,-1)`로 프로브해야 하고, 엔진의 에러 메시지는 종류 오류와 인덱스 초과를 구분한다.** `getEquationProperties(s,p,c,-1,-1)`은 `script`를 포함한 29키 속성 객체를 반환한다(`script`, `fontSize`, `fontName:"HYhwpEQ"`, 배치/여백 등). 메시지 분류: 종류 불일치는 **`…이 아닙니다`**(`지정된 컨트롤이 표가 아닙니다` / `지정된 컨트롤이 수식이 아닙니다` / `컨트롤 N은 각주/미주가 아닙니다`), 범위 초과는 **`컨트롤 인덱스 N 범위 초과`**로 서로 다르다. 종류 판별은 이 구분 위에서만 성립한다. — **CONFIRMED.** `test:` `test/spec/doc-walk.test.mjs` — "rule 33: getEquationProperties with (-1,-1) returns the body equation's script" / "rule 33: the engine's error messages discriminate kind from out-of-range".

35. **두 컨트롤이 한 오프셋을 공유할 수 있으므로 splice 순서는 total order여야 한다.** 문단 끝을 넘겨 clamp된 수식 2개는 `getControlTextPositions`에서 `[0,0,5,5]`로 나온다(모든 섹션 첫 문단의 보이지 않는 쌍도 마찬가지로 `[0,0,…]`). splice는 **오프셋 내림차순, 동률이면 컨트롤 인덱스 내림차순**으로 돈다 — 내림차순이어야 앞선 splice가 뒤 오프셋을 밀지 않고, 동률에서 높은 인덱스를 먼저 처리해야 출력에서 **낮은 인덱스가 앞**(=문서 순서)에 온다. 정렬 안정성에 결과를 맡기지 않는다. — **CONFIRMED.** `test:` `test/spec/inline.test.mjs` — "ties: two controls at one offset render deterministically, in document order" / "splice: descending order means an earlier splice never shifts a later offset".

## 8. Tracked changes (변경 내용 추적 — 두 번째 조용한 데이터 손실)

> **핵심 원리.** 엔진은 변경 내용 추적을 **모델링하지 않는다.** 결과는 두 개의 버그 한 뿌리다 — 읽으면 이미 지워진 텍스트가 살아 있는 본문과 섞여 나오고(규칙 42), 쓰면 메모와 똑같이 저장 시 전부 파괴된다(규칙 46). 구현: `src/lib/trackchange.mjs`(무의존 CFB/레코드 파서, `lib/hwp5.mjs` 위) + `read.mjs --track-changes`.

42. **삭제된 텍스트는 `PARA_TEXT`에 물리적으로 그대로 남아 있다 — 그래서 평문 읽기는 삽입과 삭제를 섞는다.** 문단 스트림에는 아무 표시도 없다. 무엇이 "삭제"인지는 **별도의 `PARA_RANGE_TAG` 레코드**가 문자 범위로 정한다. 그래서 `read.mjs`는 그 텍스트를 그대로 찍었고, 에이전트는 저자가 이미 제거한 문장을 살아 있는 본문과 구분 없이 읽었다. **실문서 측정: 삽입 4,316자 / 삭제 618자가 조용히 섞였다.** 지금은 **실제로 변경추적이 있을 때만** stderr에 경고하고(`TRACKED CHANGES … 1 insertion(s), 1 deletion(s)`), `--track-changes`로 종류별 분리 열람이 가능하다. 변경추적이 없는 문서의 stdout/stderr는 **한 글자도 바뀌지 않는다** — 40케이스 골든 베이스라인이 그것을 고정한다. — **CONFIRMED (실문서 실측; 커밋 `0113106`).** `test:` `test/spec/trackchange.test.mjs` — "scanRecordStream: counts by kind and lifts each range's covered text" / "read (plain): warns that the body text MIXES insertions and deletions" / "read (plain): a clean document emits NO tracked-change output at all" / "read --track-changes: lists each change with kind, id, author and text".
43. **탐지에는 두 개의 독립 신호가 필요하다 — FileHeader bit 14 AND 보강(DocInfo tag 96/97 또는 BodyText tag 70).** `hasTrackChanges = flagBit && corroborated`. **bit 14 단독은 과다보고한다** — 비트가 켜져 있고 실제 변경은 0인 실문서가 관측되었다. 그 플래그는 *기능이 켜졌다*를 기록할 뿐 *무엇이 바뀌었다*를 기록하지 않는다. 비트 하나로 모든 편집을 막는 가드는 아무도 지키지 않는 가드가 된다. 반대로 보강만 있고 비트가 없어도 판정하지 않는다. — **CONFIRMED (합성 레코드 스트림 + 실샘플).** `test:` `test/spec/trackchange.test.mjs` — "detectTrackChanges: flag bit + corroboration → hasTrackChanges" / "detectTrackChanges: the FLAG BIT ALONE never sets hasTrackChanges" / "detectTrackChanges: corroboration WITHOUT the flag bit is also not a verdict" / "detectTrackChanges: hasTrackChanges is a real boolean, always" / "detectTrackChanges: exact key set — every one of these is read by the guard".
44. **`HWPTAG_TRACK_CHANGE`(tag 32)는 CONFIG 레코드이지 편집 기록이 아니다 — 세면 오탐 100%다.** 이 엔진이 만드는 **빈 문서에도 정확히 하나** 들어 있고(옛 픽스처 중에는 0개인 것도 있다), 따라서 개수를 세면 엔진이 만든 모든 파일에서 거짓 양성이 난다. **존재도 부재도 아무것도 증명하지 못한다** — 그래서 `lib/hwp5.mjs`는 이 태그를 `TAG.TRACK_CHANGE_CONFIG`로 명명한다. 진짜 변경 레코드는 **tag 97(DocInfo)**과 **tag 70(BodyText)**이다. 진단용 `countTrackChangeConfigRecords()`는 판정에 참여하지 않고, 오직 "tag 32가 있어도 판정은 여전히 false"라는 선택성을 테스트가 직접 단정하기 위해 존재한다. — **CONFIRMED (실샘플).** `test:` `test/spec/trackchange.test.mjs` — "HWPTAG_TRACK_CHANGE_CONFIG (tag 32) is present in real samples and proves NOTHING" / "clean samples: scanned (supported), no flag bit, no changes, no entries"; `test/spec/corpus.test.mjs` — "corpus: tracked-change detection stays selective".
45. **tag 70 페이로드 레이아웃과 파싱 계약.** `PARA_RANGE_TAG` 본문은 **12바이트 엔트리의 평탄 배열**이다: `u32 start`(문단 내 첫 wchar), `u32 end`(마지막+1), `u32 tag` — 이 중 **상위 바이트 = 종류**(**16 Insert / 17 Delete / 18 CharShape / 19 ParaShape**), **하위 24비트 = 변경 id(1-based)**로 DocInfo 변경 레코드와 이어진다. 잘린 마지막 엔트리는 추측하지 않고 버린다. 오프셋은 **WCHAR 위치**이므로, 인라인 컨트롤을 접어버리는 읽기용 디코더(`decodeParaText`)로 슬라이스하면 범위가 통째로 밀린다 — 그래서 별도의 1:1 wchar→슬롯 디코더를 쓴다(8-wchar 인라인 컨트롤은 빈 슬롯 8개). 인식하지 못한 kind 바이트는 **세지 않되 보강 신호로는 인정한다**(모르는 것 때문에 "깨끗하다"고 말하지 않기 위해). **저자 귀속은 보수적이다**: tag 97의 내부 레이아웃이 공개 문서화되어 있지 않고 검증할 픽스처도 없으므로, 저자가 **정확히 한 명일 때만** 모든 변경을 그 사람에게 귀속하고 그 외에는 `author: ""`로 비운다 — 남의 편집에 틀린 이름을 확신에 차서 붙이는 것보다 이름이 없는 편이 낫다. — **CONFIRMED (합성 스트림; `hwp5.buildRecords`는 `walkRecords`의 역함수로 이 목적에 존재한다).** `test:` `test/spec/trackchange.test.mjs` — "parseRangeTags: decodes {start,end,kind,id} for all four tracked kinds" / "parseRangeTags: the high-byte/low-24-bit split holds at the boundaries" / "parseRangeTags: a trailing partial entry is dropped, not guessed at" / "scanRecordStream: range offsets are WCHAR positions, so inline controls count" / "scanRecordStream: an unrecognized range kind is not counted but still corroborates" / "readTrackChanges: entry shape is {index,kind,author,id,text,location}" / "readTrackChanges: with several authors, attribution is left EMPTY, not guessed".
46. **변경추적 문서를 편집하면 메모와 똑같이 변경이 파괴된다 — `assertTrackChangeSafe`가 기본 차단한다.** 변경 데이터는 오직 섹션 `raw_stream` 패스트패스로만 살아남으므로(규칙 29·§2a와 동일 뿌리), 그 섹션을 건드리는 **첫 편집**이 IR 재직렬화로 전부 지운다 — 삭제 범위가 아직 들고 있는 **원문까지** 함께. 그래서 `assertTrackChangeSafe`는 `assertMemoSafe` 계약의 의도적 복제다: exit **`UNSAFE(6)`**, 우회는 **`--allow-trackchange-loss`** 뿐, 거절 메시지는 무엇을 지키는지·먼저 어떻게 들여다보는지(`read.mjs --track-changes`)·어떻게 강행하는지를 모두 이름으로 말한다. **모든 write 스크립트가 메모 가드 옆에서 이 가드를 함께 호출한다.** 스캔 에러는 절대 차단하지 않는다(자기 버그로 fail-closed하는 가드는 삭제되는 가드다). 진짜 변경추적 픽스처는 **커밋할 수 없다** — Delete 범위가 원문을 보존하고 컨테이너가 저자 실명·`PrvText`·`HwpSummaryInformation`까지 담으므로, 실패한 테스트 하나가 남의 사문서를 공개 git 히스토리에 영구히 남긴다. 대신 합성 컨테이너로 실제 파일을 만들어 실제 스크립트를 spawn하고(가드는 엔진 로드보다 먼저 돈다), 실문서를 가진 사람을 위해 `HWP_TRACKED_FIXTURE`로 end-to-end 경로를 옵트인한다. — **AGENT-SIDE (구현됨: `lib/trackchange.mjs`).** `test:` `test/spec/trackchange.test.mjs` — write 스크립트 8개(`replace` / `edit_text` / `edit_cell` / `table` / `format` / `header_footer` / `footnote` / `unlock`) 각각에 대해 생성되는 "GUARD: replace.mjs refuses a tracked-changes input with UNSAFE(6)" / "GUARD: replace.mjs --allow-trackchange-loss disarms the guard (exit is NOT 6)" / "GUARD: replace.mjs never blocks a clean document" 3종, 그리고 소스 레벨 불변식 "GUARD: every write script that guards memos also guards tracked changes" / "assertTrackChangeSafe: clean input is a no-op, tracked input throws the exit" / "assertTrackChangeSafe: a scan error never blocks and never warns" / "HWP_TRACKED_FIXTURE: real-document end-to-end (skipped unless set)".
47. **HWPX는 `supported:false`를 반환한다 — "변경 없음"이 아니라 "확인하지 않음"이다.** OWPML은 변경추적을 자체 XML 요소로 담지만, 스캐너를 검증할 **진짜 변경추적 `.hwpx`가 없다.** 스캔하지 못한 컨테이너에 대해 "깨끗하다"고 답하는 것은 이 모듈이 막으려는 바로 그 조용한 거짓말이므로, HWPX(및 인식 불가 컨테이너)는 `supported:false`로 답한다. 호출자는 이것을 clean으로 읽어서는 **안 된다**. 추측으로 차단하는 것도 똑같이 틀리므로 `assertTrackChangeSafe`는 **차단하지 않고 경고한다**. `read.mjs --track-changes`는 `NOT CHECKED`를 찍고 `no tracked changes`는 절대 찍지 않는다. — **AGENT-SIDE (구현됨) / 기저 동작은 미검증(UNVERIFIED).** *비는 것: 변경추적이 실제로 들어 있는 `.hwpx` 한 개. 그것이 생기면 (a) OWPML 요소를 읽는 스캐너와 (b) 이 규칙을 대체할 CONFIRMED 규칙을 쓸 수 있다.* `test:` `test/spec/trackchange.test.mjs` — "HWPX: detectTrackChanges reports supported:false — 'not checked', not 'clean'" / "HWPX: assertTrackChangeSafe warns but does NOT block" / "read --track-changes: HWPX says NOT CHECKED rather than claiming none".

## 9. Sections / snapshots / performance (섹션·스냅샷·성능 — AGENT-SIDE)

> **핵심 원리.** "지난주 이후 뭐가 바뀌었나"에 파일 단위가 아니라 **섹션 단위**로 답한다. 파일 단위 답("파일이 다릅니다")은 쓸모없고, 압축 CFB 컨테이너의 바이트 diff는 그보다 나쁘다 — `.hwp`는 아무것도 편집하지 않고 다시 저장만 해도 바이트가 사방에서 바뀐다.

48. **스냅샷은 노드의 OWN TEXT만 저장한다 — 절대 서브트리 텍스트가 아니다.** 노드가 자기 서브트리를 통째로 담으면 3.2.4의 문장 하나를 고쳤을 때 3.2.4·3.2·3·루트가 **모두** "변경됨"으로 보고된다 — 편집 하나에 변경 섹션 넷, 트리가 깊을수록 거짓말이 커진다. own text면 편집된 문단당 정확히 노드 하나가 바뀐다. (같은 이유로 `blockIndex`/`headEnd`는 기록만 하고 **매칭에는 쓰지 않는다**: 맨 앞에 문단 하나만 넣어도 모든 인덱스가 밀린다.) — **AGENT-SIDE (구현됨: `lib/snapshot.mjs`).** `test:` `test/spec/snapshot.test.mjs` — "OWN TEXT ONLY: editing a leaf reports exactly one changed node" / "OWN TEXT ONLY: the edited leaf's ancestors are reported as unchanged" / "OWN TEXT ONLY: a parent's own paragraph changes the parent, not its children".
49. **메타 게이트: `sourceFormat`·`tableMode` 불일치는 REJECT, 탐지기/렌더러/엔진 버전 불일치는 WARN, 메모 감소는 크게 WARN.** 두 베이스라인은 **같은 방식으로 만들어졌을 때만** 비교 가능하다. 같은 문서를 `.hwp`로 읽은 것과 `.hwpx`로 읽은 것은 서로 **~100% 변경**으로 diff되고, `tableMode: body`와 `cells`도 마찬가지다 — 그것을 결과라고 내놓는 것은 확신에 찬 거짓말이므로 호출자가 exit `USAGE(2)`로 바꾸고 재베이스라인을 지시한다. 나머지(detect, headingRegex, 학습된 ladder, render/eqn/tableRender/engine 버전)는 diff를 시끄럽게 만들 뿐 답은 여전히 그 안에 있으므로 **경고 후 진행**한다. **메모 개수가 줄었으면 `loud` 경고**다 — diff를 보고 이어서 편집하려는 사람은 메모가 파괴되는 바로 그 자리에 서 있다(CLAUDE.md 규칙 4). > 범례: **WORKS** = export→reload 왕복 생존 검증. **FAILS-SILENTLY** = in-memory 성공 보고하나 reload 시 편집 없음(verified=false), 에러 없음 → **스킬 금지 경로**. **HANCOM-REJECTED** = throw 또는 한컴이 산출물 거부(하드 실패). **BLOCKED-DATA-LOSS** = 편집 자체는 동작하나 저장 시 **엔진이 모델링하지 않는 기존 데이터**(메모, 변경 추적)를 조용히 삭제 → **스킬이 기본 차단**(exit UNSAFE(6), 각각 `--allow-memo-loss` / `--allow-trackchange-loss`로만 우회). **UNCHECKED+WARN** = 스캔 자체가 불가능해 위험 유무를 말할 수 없음 → 차단하지 않고 경고(침묵은 "확인했다"는 뜻이 되므로). **WORKS+WARN** = 동작하나 알려진 위험으로 경고 필요. *기울임 주석* = 경험적 미검증(추정).
