# 병렬 편집: 계획 재생기 vs 분할·병합 — 2026-08-27

여러 에이전트가 한 문서를 일관된 서식으로 편집하려면 두 경로가 가능해 보인다.
**측정 결과 하나는 구조적으로 막혀 있다.**

## A안. 팔레트 + 계획 재생기

```
분석 1회 → 팔레트(계약) → 에이전트 N개가 계획만 생산(병렬) → 적용기 1개가 직렬 실행 → 계약 대조
```

**어려운 지점: 문단 인덱스 밀림.** 앞 계획이 문단을 삽입하면 뒤 계획의 주소가 밀린다.

**이 레포에 이미 풀린 문제다.** `lib/blocks.mjs`가 인라인 컨트롤 splice에서 같은 문제를
**내림차순 처리**로 해결했고, 동점(같은 오프셋의 컨트롤 2개)까지 전순서 비교자로
문서화해 두었다. 문단 단위로 올리면 그대로 적용된다 — 높은 인덱스부터 적용하면
아직 적용 안 된 항목의 주소는 항상 유효하다.

깨지는 경우는 좁고 **탐지 가능**하다: 같은 주소를 두 항목이 노릴 때, 또는 한 항목의
대상이 다른 항목이 만들어낸 문단일 때. 조용히 잘못 적용하느니 거절하면 된다.

**결정적 장점: 원본을 떠나지 않는다.** 글꼴·스타일·번호매기기·메모 같은
**문서 수준 자원**이 구조적으로 보존된다.

## B안. HWP 분할 + 병합

**엔진에 문서 간 합성 경로가 없다.** 클립보드는 **인스턴스별**이다:

```
A.hasInternalClipboard() -> true
B.hasInternalClipboard() -> false     // A에서 복사한 것이 B에 없다
```

`copySelection` / `pasteInternal`은 한 문서 안에서만 동작한다. 따라서 병합은 청크를
읽어 대상 문서에 **문단 단위로 다시 만드는 것**밖에 없다.

**그 재조립의 손실을 실측했다** — 문단을 새 문서에 재생성하며 쓰기 API가 지원하는
서식을 전부 되적용한 뒤 비교:

| 실문서 6건, 텍스트 문단 67개 | |
|---|---|
| 텍스트 보존 | **67/67 (100%)** |
| 글자 크기 보존 | 67/67 (100%) |
| 스타일 이름 손실 | 1/67 (1%) |
| **글꼴 손실** | **62/67 (93%)** |

픽스처에서도 같다: `fixture-table.hwp`는 **36/36 전부** 글꼴을 잃는다(HY헤드라인M 등).
`fixture-headings.hwp`는 0/22인데, 이미 기본 글꼴만 쓰기 때문이다.

**고칠 수 없다.** 규칙 60·61: `applyCharFormat`은 글꼴을 못 바꾸고, `setCharShapeId`는
전 id에서 무동작이며, `createStyle`은 이름만 만들고 `updateStyle`은 아무것도 안 한다.
새 문서에 원본의 글꼴을 실어 나를 **어떤 API도 없다.**

여기에 더해 청크는 섹션 `raw_stream`을 떠나므로 **메모와 변경추적이 사라진다**(규칙 4·5).

**그리고 무손실 병합은 A안으로 수렴한다.** 문서 수준 자원을 지키는 유일한 방법은
**원본을 떠나지 않는 것**이고, 원본에 변경만 적용하는 것이 곧 계획 재생기다.

## 결론

| | A안 | B안 |
|---|---|---|
| 엔진 지원 | 있음 (기존 편집 API) | **없음** (문서 간 합성 경로 부재) |
| 글꼴 보존 | 구조적으로 보존 | **93% 손실** |
| 메모·변경추적 | 보존 | 청크에서 소실 |
| 어려운 문제 | 인덱스 밀림 — **전례 있음**(`blocks.mjs`) | 병합 자체 — **해법 없음** |
| 병렬성 | 판단은 병렬, 적용만 직렬(50ms) | 편집도 병렬 |
| HWPX | 영향 없음 | 출력이 `.hwp`로 제한되는 제약과 겹침 |

**A안.** B안의 병렬성 이점은 적용 단계에만 해당하는데 그 단계는 문서 하나에
50ms 미만이라 병목이 아니다. 반면 B안의 손실은 우회로가 없다.

분할 자체는 지금도 가치가 있다 — 다만 **읽기·분석용**이며(현재 `--op split`이
마크다운을 쓰는 이유), 편집 왕복 경로가 아니다.

## 재측정 조건

이 판정은 엔진 제약에 기대고 있다. 다음 중 하나라도 바뀌면 B안을 다시 봐야 한다:

- rhwp가 **문서 간 붙여넣기**를 지원(클립보드가 인스턴스 경계를 넘음)
- `createStyle` / `updateStyle`이 실제로 동작 → 새 문서에 글꼴·스타일을 실어 나를 수 있음
- `setCharShapeId`가 동작 → 문자 모양을 주소로 이식 가능
