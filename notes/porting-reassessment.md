# 포팅 재검토 — 2026-08-27

"기계적 파서가 늘었으니 Rust/Go/WASM 포팅 이득이 달라졌는가"를 다시 쟀다.
**결론은 유지된다. 다만 이유가 예전과 다르다.**

## 1. JS 코드는 실제로 늘었다

| 성격 | 줄 수 |
|---|---|
| 기계적 파서 (`hwp5` `trackchange` `memo` `blocks` `doc_walk` `tables` `objects`) | **2,732** |
| 판단·정책 (`headings` `snapshot` `format_props` `image_props` `section_diff` `verify`) | 3,320 |
| `src/` 전체 | 13,105 |

기계적 파서가 2,700줄이면 "포팅 후보"로 보이는 게 당연하다. 그래서 시간을 쟀다.

## 2. 시간은 거기 있지 않다

199MB `.hwp` (이 코퍼스 최대):

| 단계 | 시간 | 포팅으로 없앨 수 있나 |
|---|---|---|
| **엔진 파싱 (이미 Rust/WASM)** | **586ms** | 이미 Rust다 |
| 디스크 읽기 | 22–111ms | 아니다 (순수 I/O) |
| **CFB 스트림 테이블 (우리 JS)** | **69ms** | **그렇다 — 가장 큰 후보** |
| 섹션 inflate | 11ms | 아니다 (node zlib = 네이티브 C++) |
| 레코드 워크 (우리 JS) | 3ms / 32,002 레코드 | 사실상 0 |
| node + WASM 부팅 | 6ms | 아니다 |

문단이 가장 많은 문서(1,571문단)에서:

| 단계 | 시간 |
|---|---|
| 엔진 파싱 | 17–22ms |
| 엔진 텍스트 워크 | 1–2ms |
| 속성 워크 (엔진 호출 4.1ms + `JSON.parse` 3.5ms) | 11–18ms |
| 우리 JS 블록 모델 | 3–8ms |

**문서 하나를 통째로 도는 데 50ms가 안 된다.**

**정리:** 우리 JS 전부를 Rust로 옮겨서 얻는 최대치는 병적으로 큰 199MB 문서에서
**~70ms**, 보통 문서에서 **~5–10ms**다. 에이전트 왕복이 초 단위인 것에 비하면 잡음이다.

## 3. 네이티브 바이너리는 여전히 탈락

`.hwp`를 다루는 사용자의 3개 플랫폼 중 **claude.ai와 Cowork를 잃는다.**
이건 예전 판단 그대로이고, 70ms로 살 수 있는 것이 아니다.

Rust→**WASM**이면 플랫폼은 지킬 수 있다. 그러나 vendored WASM이 이미 6.9MB,
배포 zip이 2.9MB인 상황에서 **5–10ms를 위해** 두 번째 WASM 모듈과 빌드 체인을
얹는 거래다.

## 4. 진짜 발견 — 우리는 rhwp가 이미 하는 일을 다시 하고 있다

`hwp5.mjs`(365줄)가 존재하는 이유는 **rhwp가 내부적으로 파싱한 CFB를 노출하지 않기
때문**이다. API 표면 335개를 뒤졌으나 스트림·레코드·컨테이너 접근자는 **하나도 없다**
(`__destroy_into_raw`뿐). 메모·변경추적 API도 **없다** — 그래서 우리가 컨테이너를
직접 연다.

→ 우리 JS를 Rust로 포팅하는 것은 **rhwp의 내부 작업을 두 번째 Rust 코드베이스로
복제하는 일**이다. 옳은 방향은 포팅이 아니라 **업스트림 요청**이다:

1. 원시 스트림 테이블 노출 → `hwp5.mjs` 365줄과 CFB 69ms가 **동시에** 사라진다
2. 메모 / 변경추적 모델링 → `memo.mjs` + `trackchange.mjs` 699줄이 사라지고,
   규칙 4·5의 "조용한 데이터 손실"이 **가드가 아니라 해결**된다

이쪽이 포팅보다 코드도 더 줄고 위험도 낮다.

## 5. 결론

**포팅하지 않는다.** 근거가 예전과 달라졌다는 점은 기록해 둔다:

- **예전 근거:** "파싱은 이미 Rust다"
- **지금 근거:** 그것도 여전히 맞지만, 더 정확히는 — 우리 JS는 **측정 가능한 비용이
  거의 없고**(보통 문서 5–10ms), 남은 하나의 실제 비용(CFB 69ms)은 **포팅이 아니라
  업스트림 노출로 없애는 게 맞다.**

재측정 시점: rhwp가 스트림 접근자를 추가하거나, 우리 JS 단독 비용이 어떤
문서에서든 **100ms를 넘기 시작하면.**
